A PR reviewer that learns

The Self-Learning
PR Reviewer

Most AI reviewers are a static checklist. This one rewrites its own rulebook: every bug that slips past review becomes the signal that sharpens the next review — with a human approving each upgrade.

Status: live & running microsoft/amplifier-app-team-pulse Built by Sam (samueljklee)
The problem

A reviewer only catches what the checklist already knows.

The blind spots stay blind — and they repeat. Three failure modes, every team has all three:

Bugs slip past

A reviewer — human or AI — only flags what it is looking for. Whatever it is not looking for ships.

The same classes recur

Not random bugs — repeating ones. Raw writes, client-trusted auth, schema drift. Over and over.

Nobody updates the rubric

The checklist is written once and rots. The lesson lives in a senior engineer's head, not in the gate.

The insight

Your fix/revert commits are free training labels.

Every time a bug escapes, your team produces the evidence automatically: a commit whose subject starts with fix, revert, hotfix, or regression.

That is a labeled dataset of "things the reviewer missed" — generated for free, zero labeling effort. The harness just harvests it on a schedule. (The idea has deep roots: mining bug-fix commits is the classic SZZ method.)

# the learning signal — harvested weekly git log --since "7 days ago" \ | grep -iE '^[a-f0-9]+ (fix|revert|bug|hotfix|regression)' \ | head -200 > escapes.txt # anchored to the commit subject prefix, # so only real fix/revert commits count
The loop in one picture

Escapes teach the rubric. The rubric governs every review.

One artifact at the center — the living rubric. Reviews read it; escapes feed the harness; the harness proposes; you approve; the rubric sharpens. (A fully annotated version is in the appendix.)

How it works · one file, two loops

Both loops meet at a single file: pr-review-teampulse.md

Loop 1 · Inbound review

Read the rubric, then review

  • Fires on every PR (and an opt-in re-review comment)
  • Runs on the shared amplifier-app-actions GitHub Action
  • First instruction: "read the rubric" — team rules layered on a generic 5-check frame
Loop 2 · Improvement harness

Harvest escapes, propose upgrades

  • Weekly: gathers fix/revert commits as the learning signal
  • An Attractor pipeline judges and rewrites the rubric
  • Opens one proposal PR — a maintainer merges it, and the rubric sharpens

Why this is actually different

The novel part isn't that it learns.
It's that the rulebook is disciplined to prune itself.

Self-improving AI is everywhere — RLHF retrains weights, DSPy and OPRO auto-tune prompts. They optimize a target automatically, with no line-by-line human merge and no shrink discipline — the policy only grows, and you can't read it as a checklist.

The closest analog is Dependabot: bot proposes, human merges. Same safe shape — the difference is the merged artifact is a legible policy that prunes itself, not a version bump.

The distinctive mechanism

Every candidate rule must first pass one gate — "rubric rule, or CI lint?" — that actively removes scope from the policy. With ≥2-of-3 consensus and out-of-scope memory, the rubric stays bounded (≤180 lines) — and no rule enters without a human merging that exact line.

Built on shared Amplifier capabilities

We didn't build a reviewer from scratch.
We composed two team capabilities into a loop.

Building block 1

Amplifier's Attractor pipeline

Building block 2

The pattern is the point, not the parts: any DOT/pipeline runner (LangGraph, or a plain Python loop) plus any CI-driven reviewer can stand in for these two. The Amplifier pieces just made it a one-day assembly.

The safeguards

Automation that can't run away with itself.

Stays lean

Hard ≤180-line budget; a judge routes mechanical checks to CI lint, not the rubric. The defining discipline: refuse to grow.

No-fiat consensus

≥2 of 3 independent lenses must agree to keep a rule. No single over-eager model can bloat the gate.

Human merge gate

Automation does the boring part — gather, propose, judge. The maintainer owns the merge. Drift-proof.

Out-of-scope memory

Rejected proposals are remembered under ## Out of scope — never wastefully re-proposed.

Cost to run: one weekly cron job, plus ~5–10 min for a maintainer to skim one proposal PR. The harness opens exactly one PR and overwrites the previous proposal — it never queues a backlog. No standing service to babysit.

Proof · what the rubric actually encodes

Six real rules, each traced to escapes it now catches.

1

"Green" CI isn't green

smoke is the only hard gate; test carries ~19 known failures. A failure is the PR's fault only if it's absent at the parent.

2

data/core/ is read-only

New values go to data/overlay/, merged at read time. Direct edits to core are flagged.

3

Writes go through validated_write

Raw json.dump into data/ is rejected by the no-raw-data-writes gate.

4

Generated artifacts, never hand-edited

openapi.json + api.ts come from Pydantic via make regen-schemas; new fields mirror into the overlay schema.

5

Mutating routes need explicit authz

Four separate PRs fixing missing checks proved implicit coverage isn't enough. Identity matches the exact (provider, subject) tuple.

6

release-please owns the changelog

Don't flag a missing CHANGELOG.md edit; what matters is a valid conventional-commit PR title.

Representative — the kind of finding rule 5 now forces
+ @router.post("/api/members/{id}") + def update_member(id: str, body: MemberIn): ... # no authz guard

Review comment: This route mutates state but has no require_admin / require_self_or_admin check — any authenticated viewer can write. Add an explicit authz guard. (rubric §2 · API & identity)

Evaluate mode · measures, never mutates

How do you trust a reviewer that rewrites itself?

You instrument it. A separate evaluate run backtests proposals against a historical rubric snapshot and gates on two scores — it never touches the live rubric.

Recall

Did it catch a known class of escape? Misses fail the gate.

Dedup

Did it avoid re-proposing covered rules? Noise fails the gate.

Honest status: the loop is young — 6 rules in. We don't yet claim per-class escape-reduction numbers. What we claim is that the measurement is wired in, so "is the reviewer getting better?" becomes a number we can gate on, not a vibe.

Steal this pattern

Got CI and an agent? You can build this. Here's the skeleton.

# improve-rubric.yml — weekly; opens ONE self-refreshing proposal PR on: schedule: [{ cron: '0 16 * * 1' }] workflow_dispatch: jobs: improve: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 with: { fetch-depth: 0 } # full history for git log - run: git log --since '7 days ago' \ | grep -iE '^[a-f0-9]+ (fix|revert|bug)' > escapes.txt - run: ./run_pipeline.sh escapes.txt RUBRIC.md # propose-judge-rewrite (prev slide) - run: gh pr create --head auto-improve ... # refresh, never duplicate

1 · Harvest the labels

Grep fix/revert commits — your "what got missed" dataset, free.

2 · Judge, don't dictate

Independent lenses, ≥2 must agree; gate every rule on "rubric, or CI lint?" Keep a ## Out of scope list so rejects never return.

3 · Keep the human

Automate gather / propose / judge. The maintainer owns the merge.

A reviewer that never learns is debt. Make your escapes pay rent.
