The Project

AMP Browser: a self-hosted PWA reachable anywhere over Tailscale

A self-hosted file browser built as a Progressive Web App. It runs on a Mac Mini and a Raspberry Pi, accessible anywhere over Tailscale — a mesh VPN that gives every device a private, encrypted connection with its own MagicDNS hostname.

Act I • The Symptom

It worked on the Mac, but the iPhone couldn't find the server

The developer returned to a stubborn problem — and couldn't remember what they'd already changed, or in which session:

"HTTPS works on my MacBook browser and as a PWA. But I can't access via any mobile browser. It just returns 'the site can't be reached — server's IP address could not be found.'"

HTTPS looked fine. The server looked fine. Something else was broken — and it only affected the iPhone.

Act III • The Smoking Gun

One dash in tailscale status explained everything

The critical clue was a single character — the iPhone's connection state:

$ tailscale status 100.x.x.x home-server user@ macOS active 100.x.x.x ampworker user@ linux active 100.x.x.x iphone user@ iOS -

That - beside the iPhone: Tailscale wasn't connected. Without it, MagicDNS can't resolve *.ts.net hostnames and the phone can't route to 100.x.x.x. Not a server bug. Not an HTTPS bug. A DNS resolution failure — the phone literally couldn't find the server.

The Investigation

Three agents proved the server was innocent

Amplifier dispatched a coordinated investigation — each agent probing a different layer at once. Every diagnostic came back green: HTTPS active (PID 43784, port 8080), Let's Encrypt certs valid through May 2026, port open on the Tailscale interface. The server was fine, which is exactly what pointed the hunt elsewhere.

Diagnosis

One symptom was really three stacked bugs

"HTTPS isn't working on my iPhone" was never one problem. It was a layer cake uncovered across multiple sessions:

Layer 1 — Hostname
socket.gethostname() returned "mac.lan" instead of "home-server". Certs not found. Fixed.
Layer 2 — Paths
Cert directory was /etc/pibrowser/certs and the service file still had /home/pi/ paths -- the old project name. Fixed.
Layer 3 — DNS/VPN
The iPhone's Tailscale was disconnected, so MagicDNS never resolved. The real ghost.
Lessons

What this debugging hunt teaches

1. The reported problem is rarely the real one
"HTTPS doesn't work on my phone" was actually "my VPN client isn't connected." Start from the symptom, not the assumed cause.
2. Silent failures are the worst failures
The server silently fell back to HTTP with no error, no log, no warning. Design systems to fail loudly.
3. Session memory turns debugging into archaeology
Recovering full context from prior sessions -- and running code review, live diagnostics, and history analysis in parallel -- found the answer faster than any single linear thread.
