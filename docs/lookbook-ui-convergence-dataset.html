The Problem
That tree is normally invisible until it's too late to change it

No structural preview

You can't know what components will be generated before running generation. The output — the tree, the depth, the node count — is a surprise every time, even from the same prompt.

The pattern exists — it's just uncaptured

AI-assisted UI generation isn't random. Similar prompts tend to produce similar component topologies. That convergence pattern has never been systematically collected or studied — so it can't yet be predicted.

If the topology is invisible before generation, the question is whether it's predictable at all. Sage's own iterations give the first answer.

The payoff: By v2 the structural skeleton is established — the major nodes are all present. v3 doesn't restructure; it specifies. The topology converges before the visual fidelity does — the first evidence that prompt → tree behaves like a learnable mapping, not a coin flip.
Meet Lookbook
Lookbook is a dataset built to make that mapping predictable
Not a gallery of pretty screens — a corpus of (prompt → component tree) pairs, captured with structure intact, so AI-assisted UI generation can eventually be reasoned about before it runs.

What makes it a dataset, not a gallery

A typical lookbook is a visual showcase. This one captures the structure behind the visuals — the component tree with nesting depth, node count, and iteration history — so the mapping can be studied across many examples.

Iteration snapshots are first-class data

Capturing v1, v2, and v3 of each app isn't just documentation — it records how the tree evolves as prompts sharpen. That convergence path (as Sage just showed) is itself a signal.

The Hypothesis
The bet: prompt → component tree is a learnable function
f : PromptSpace → ComponentTreeSpace
Given enough (prompt, tree) pairs, derive the mapping between them.
f("Build Claude.ai chat with artifacts, thinking blocks, Projects sidebar")
→ { root: SageLayout, nodes: 9, depth: 3, loc: 1665 }
g : ComponentTreeSpace → PromptSpace (the reverse)
g({ root: SageLayout, children: [Sidebar, ChatArea, ArtifactsPanel] })
→ "Build a Claude.ai-style agentic chat interface with..."
One claim: if f exists, you can preview the topology a prompt will produce before generating a line of code. Deriving it needs data — which is what the collection method supplies.

The applications are still hypothetical

What's Next
Get the corpus to ten — then the patterns become visible

1. Contribute data points

Build an app with Amplifier's UI Studio pipeline, capture the component hierarchy, and add the (prompt, tree) pair to lookbook. No minimum LOC, no minimum quality — a documented prompt and a captured tree is a valid point.

2. Canonicalize the schema

The entry format is still a draft. It needs a formal JSON Schema, a standard tree serialization, and a convention for iteration snapshots that enables comparison across frameworks.

3. Analyze at 10+ entries

With ten or more points, ask which nodes recur, which structures cluster, and whether prompt patterns predict topologies. Patterns need minimum density before they're visible.
