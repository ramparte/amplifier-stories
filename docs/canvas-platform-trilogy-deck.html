The Starting Point

Canvas had grown organically — so we planned three shippable phases

Each project type owned its own rendering. Hooks were duplicated. Fullscreen was a monolith nobody wanted to touch. The fix: three phases, each merging to main on its own.

The problems
  • CanvasCard.tsx — 319 lines, 6 inline hooks, a full send pipeline baked in
  • Each plugin registered cardBody, headerActions, contextProvider — duplicated per type
  • Fullscreen = legacy TerminalView monolith, sharing nothing with card-mode rendering
Phase 1
Clean Before You Build
Remove 2 dead types, rename 5 for clarity, add grouping, clear orphaned DB records (migration 022).
Phase 2
Platform Takes the Wheel
CanvasCard owns all rendering. Plugins become pure config objects. ~850 lines of infrastructure deleted.
Phase 3
The Fullscreen Experience
A modern two-zone FullscreenCard replaces TerminalView. Session logic extracted into one shared hook.

Phase 2: the platform took the wheel, plugins became pure config

The biggest structural shift. CanvasCard becomes the engine; plugins hand over their components and shrink to a description.

Phase 3 · PR #65 · Merged Feb 21

Phase 3: one hook, one card, one path to fullscreen

Session logic collapsed into a single shared hook; fullscreen stopped being a separate monolith. CanvasCard: 319 → 83 lines (−74%).

Before
  • onCardFullscreenEnter → setView('terminal')
  • App renders legacy TerminalView monolith
  • TerminalView owned layout, hooks, message input — everything
  • CanvasCard: 319 lines, 6 inline hooks, full send pipeline
After
  • onCardFullscreenEnter → setView('fullscreen')
  • App renders two-zone FullscreenCard
  • Both cards share useProjectSession — one source of truth
  • CanvasCard: 83 lines, zero inline hooks
