The complication · Sessions 1–3
The Machine Is Only as Good as the Spec
Hand it a loose spec and it stalls. Phase 1 used light specs and burned 2 sessions to ship just 5 features — the bottleneck was never the machine.
Phase 1 · Light Specs
2 sessions

Full bar = baseline effort
✗ No explicit mock patterns
✗ No code quoted in spec

🧠
Loose specs make the machine guess.
Ambiguous mock patterns create failing tests. Undefined scope invites the machine to optimistically build things you didn't ask for — and each miss costs another whole session.
Garbage in, garbage out. The developer didn't need to code faster — the specs needed to get sharper.

The 6 Spec Quality Rules
  • 1
    Quote current code in the spec. The machine can't refactor what it can't see.
  • 2
    Show vi.mock() patterns explicitly. Pattern ambiguity creates test failures that cost extra sessions.
  • 3
    Scope each spec to ≤5 files. 5-file scopes ship. 15-file scopes get stuck.
  • 4
    Infra specs need human setup steps. List API keys and cloud resources as pre-conditions.
  • 5
    Scope section is mandatory. "In scope: X. Out of scope: Y." Without it, the machine over-extends.
  • 6
    Add a scope guard to session instructions. "Do not build anything not in the spec." Belt and suspenders.
The pattern is replicable. Start with one feature, apply the 6 rules, and let the machine ship it.
