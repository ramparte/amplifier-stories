The Claim

The recipe declares parallel: 3

# parallel-analysis-recipe.yaml - id: "run-content-checks" foreach: "{{content_check_definitions}}" parallel: 3 agent: "foundation:zen-architect" instruction: "Analyze {{item.name}}..."

That one line is the whole claim: run these validation checks three at a time instead of one after another.

The Problem

A config flag declares intent,
not execution

The YAML says what should happen. It proves nothing about what the executor actually did at runtime. A flag could be ignored, mis-wired, or silently serialized.

Configuration isn't proof. We needed evidence of actual concurrent execution — something the running system itself produced.
The Method

Correlate start timestamps
from child agent sessions

  • 1 Locate the recipe execution session and its child agents
  • 2 Extract start/end timestamps from each spawned agent
  • 3 Map timestamps to individual validation check types
  • 4 Analyze for temporal overlap — concurrent starts prove parallelism
Key insight: if agents start within milliseconds of each other, they were launched concurrently by the executor — not queued one behind the next.

Architecture

Under the hood: gather + a Semaphore(N)

Recipe YAML
parallel: 3
→
Executor
asyncio.gather
→
Concurrency
Semaphore(N)
Unbounded: parallel: true
# All items launch at once await asyncio.gather( *[run_item(i) for i in items] )

Every foreach item runs concurrently. That's the 317ms cluster from slide 1.

Bounded: parallel: N
# Semaphore limits concurrency sem = asyncio.Semaphore(N) async def limited(item): async with sem: return await run_item(item)

At most N run at once — the two-wave pattern you just saw.

The Honest Limit

Timestamps prove runtime —
but they can't be git-verified

The code is confirmed in the repo. The timing evidence is not something a commit can re-prove.

Proven in git

Bounded parallelism landed in commit 997b85e (Brian Krabach, Jan 7 2026) in microsoft/amplifier-bundle-recipes, using asyncio.Semaphore. 19 of 21 executor commits are his.

Not claimed

The timestamps are example session data, not reproducible from git. A self-documenting parallel_metrics block is proposed, not confirmed shipped.

This is why the deck shows raw start times: the numbers do the arguing, honestly labeled.

Takeaway

Verify, don't trust.

  • ✓ Configuration declares intent — timestamps prove execution
  • ✓ Session archaeology — child-agent start times tell the real story
  • ✓ Quantify the win — “parallel” means nothing without wall-clock numbers
  • ✓ Build in observability — make parallel systems self-documenting next time

Parallel execution is active in the recipe executor today. Try parallel: true on your foreach steps.
