The Blind Spot

Automated validation can’t see
what a design expert sees

Rule-based checks confirm a document is structurally and factually correct. They stay silent on whether it actually reads well — so we quietly assumed validation could only make quality go up.

✅
Structure — checked
Schema compliance, required fields, format correctness
📋
Content — checked
Completeness, accuracy, technical correctness
❓
Design quality — unseen
Does it catch what a design expert would notice? Nothing in the pipeline can answer that.

Why this matters
An expert observer revealed validation is not purely additive. Without it, we’d have shipped v3 believing it was strictly better than v0 — and never known what we gave up.

Beyond the scoreboard

The observers caught issues no rule could

Beyond moving numbers, DI feedback surfaced qualitative problems that structure-and-content validation has no way to detect:

  • External reference accessibility
    @shadow:context references aren’t accessible to all readers — the doc assumes internal tooling knowledge.
  • Platform bias
    Linux/macOS-weighted examples with minimal Windows coverage, potentially excluding a segment of users.
  • Cognitive load
    The Dev Patterns intro front-loads 6 concepts before any example — overwhelming for newcomers.
  • Information prominence
    Critical naming-convention guidance buried in the wrong section, reducing discoverability.

These insights came from one document generation run. Additional documents may surface different patterns.

Where this goes

From observing to preventing

Observation proved the value. The next step is to feed DI insights into outline refinement — fixing issues before generation instead of only measuring them after.

Potential evolution
Today: Observe → Report
Tomorrow: Observe → Refine → Generate → Validate
