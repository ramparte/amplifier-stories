What Resolve Is

Three steps: describe intent, resolve it autonomously, deliver a PR

📝

1 · Describe Intent

A user writes a spec — what the software should do, defined as observable HTTP behavior. No implementation details.

⚙️

2 · Resolve Autonomously

A resolver instance explores the codebase, plans changes, implements them, tests in a live environment, and iterates until done.

🚀

3 · Deliver a Pull Request

The platform promotes results back to GitHub or Gitea as a PR. Working code, tested and ready for review.

Keep those three steps in mind — the question the rest of the deck answers is who does step 2, and how the platform stays out of its way.

The Complication

Every "AI that writes code" forces the same bad trade-off

The monolith you can't extend

One giant AI system owns the whole pipeline. It works — until you want a different coding strategy, and there's no seam to plug into.

The bespoke pipeline you rebuild

Hand-wire git, containers, testing, and promotion for one approach. Then a new approach arrives and you rebuild the plumbing from scratch.

Either way, a single coding approach is just one strategy — and treating each new one as a new platform doesn't scale.

The Resolution

The factory for factories: a thin host, and the strategy is a plugin

Resolve owns lifecycle, routing, and validation. Resolvers own all the intelligence. A new coding approach is a new resolver — not a new platform.

"The host is a thin lifecycle/routing/validation layer. Resolvers own all resolution semantics. New capabilities are added as new broker handlers conforming to CapabilityHandlerProtocol."

— design/ARCHITECTURE.md

The next three slides show the three things that make this real: the boundary, the plug, and the trust.

The Boundary · Claim 1

Four layers draw one line: the host runs it, resolvers decide it

1

App Shell

React SPA — A2UI rendering surface with optional viewport extensions for custom resolver visualization.

2

Headless Core

FastAPI service — instance lifecycle, broker, resolver registry, auth, observability. ~24,000 lines of source.

3

Resolvers

One child process per phase, speaking JSONL over stdio via amplifier-resolver-sdk. Pluggable — discovered via entry points.

4

Per-Instance Services

Sidecar containers: Gitea, GH-router, DTU spawn, Reality-Check spawn. New capabilities via CapabilityHandlerProtocol.

Layers 1, 2, and 4 are infrastructure the host owns. Layer 3 is where a strategy lives — the only layer a new coding approach has to touch.

The Plug · Claim 2

A2UI v0.9 makes any resolver interchangeable — and one command registers it

🧲

Attractor

Multi-stage AI pipeline — plan, implement, test, review. Ships as a submodule at amplifier-bundle-attractor.

💻

Dev Machine

Interactive resolver that pairs with a human developer in the loop for guided implementation.

📊

Dot Graph

Specialized resolver for architecture diagrams and codebase visualization.

All three speak the same 12-member protocol — schema-driven input, typed messages, SSE events. amplifier-resolve resolver add <spec> validates a new one in an ephemeral container; it inherits workspace, git sidecars, and promotion for free.

The Trust · Claim 3

Reality Check trusts what the code does — not how it's written

However a resolver produced its code, the platform validates it the same way: by exercising observable HTTP behavior against live services.

# Create an instance — the spec is behavior, not implementation curl -X POST http://localhost:10120/instances \ -d '{"resolver": "attractor", "input": {"spec": "Add GET /api/version", "repo": "org/repo"}}' # Watch it work in real time, then collect the PR curl -N http://localhost:10120/instances/{id}/events

Because trust is behavioral, the platform doesn't care which strategy wrote the code — which is exactly what lets strategies stay pluggable.
