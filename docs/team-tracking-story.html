The challenge

Naive recipes break
three ways at scale

Each failure only showed up once real batches ran — and each one could halt an entire run.

  • Crashes on missing files — sync-session died whenever a session lacked an events.jsonl.
  • Death by API calls — multiple GitHub calls per session made large batches slow and rate-limited.
  • ARG_MAX overflow — 580KB+ transcripts exceeded shell argument limits when passed on the command line.
Pattern 1

Every step must always
produce output

The crash's real cause: the template engine resolves all variables before it checks any conditional — so a missing file blows up before the "if exists" guard can skip it. The fix is to move the conditional inside the bash.

# ✓ Option A: conditional inside bash if [ -f "${SESSION_DIR}/events.jsonl" ]; then cat "${SESSION_DIR}/events.jsonl" else echo "" # always return output fi

Golden Rule: all recipe steps must always produce output, even an empty string. The bash layer handles file existence; the recipe layer handles data flow.

The payoff

The patterns are
the real deliverable

The tracking feature is switched off — but the engineering it forced out is not tied to it. The "always output" golden rule, local-first reads, and stdin piping are recipe patterns any Amplifier bundle can reuse.

Why it endures: these fixes aren't about team-tracking at all. They're about how the recipe engine evaluates templates, how bulk work should touch the network, and how bash steps move large data. Turn the feature off; the lessons stay on.

Pattern 2

Read local files first,
skip the API

Original approach

Multiple GitHub API calls per session

  • Fetch session metadata via API
  • Download events.jsonl and transcript
  • Parse, analyze, repeat

Result: slow for large batches, rate-limited by GitHub.

Optimized: local-first

Direct reads from ~/.amplifier/sessions/

  • Parse local session files straight from disk
  • Zero API calls for analysis
  • Batch commits cut API usage by ~85%

Result: significantly faster, no rate limiting.

Pattern 3

Pipe large data through
stdin, never arguments

Before

Passing data via arguments

curl -X POST --data "$TRANSCRIPT"

❌ Fails on files past the ARG_MAX limit

After

Piping via stdin

echo "$TRANSCRIPT" | curl --data-binary @-

✓ Handles 580KB+ files reliably

Lesson: in recipe bash steps, always pipe large data through stdin rather than passing it as shell arguments.

The through-line

Reliability came from where logic lived, not more code

All three fixes share one move: push the decision to the layer that can actually handle it. Conditionals belong in bash, not recipe logic. Data access belongs on disk, not the network. Big payloads belong in stdin, not argv.

What it enabled: 19 recipes across sync, catchup, reporting, and research pipelines ran the same way — the same discipline that keeps one step alive keeps a hundred-session batch alive.

Take it with you

Three rules for
recipes at scale

  • Always output — every recipe step returns something, even an empty string.
  • Local-first — prefer filesystem reads over API calls for bulk work; batch your commits.
  • Stdin for size — pipe anything large; never trust the command line with 580KB.

Turn the feature off. Keep the engineering.
