The Fleet

Five machines,
building around the clock

The foundry runs a fleet of autonomous dev machines — each one a full dev loop working its own project, all running in parallel with no human at the keyboard.

The five autonomous machines

  • word4 · botslack · openM365 · safeguard · universal-app
  • Each ships software autonomously: spec → build → test → commit, on repeat
  • Productive when everything works — the real question is what happens when it doesn't

They were like factories with no control room — humming when every line ran, helpless the moment one jammed.

The Problem

Five machines,
zero visibility

When something breaks at 2 AM, nobody knows until morning — and by then hours of compute are already gone.

🙈

Blind Operations

Five machines running autonomously with no unified view of what's happening across the fleet.

💥

Silent Failures

A missing Python package kills a container. A stale lockfile halts a build. Hours wasted before anyone notices.

📱

No Remote Access

Checking status meant SSH into the host. No way to glance at fleet health from a phone or another machine.

The machines were productive when everything worked — and helpless when anything broke. Visibility had to come first.

Self-Healing

Machines that
fix themselves

Two layers of auto-recovery mean most breakages never reach a human: Pattern I for container crashes, and an AI agent that reasons about broken environments.

Pattern I: Auto-Heal

Detects crash loops and missing packages straight from container logs, runs pip install or uv sync, and restarts — no human in the loop.

  • Parse ModuleNotFoundError from log output
  • Install missing package, verify, restart
  • Escalate if 3 attempts fail

Env-Remediation Agent

An AI agent (288 lines of protocol) that reasons about a broken stack instead of just matching regexes. Fast-path catalog lookup, then independent diagnosis.

  • Reads a hints catalog of known fixes first
  • Falls back to independent reasoning
  • 3-attempt hard limit, then structured escalation

The agent may modify lockfiles, reinstall node_modules, recreate .venv, or apt-get missing tools — but it may never touch application source code. If it can't fix the environment in 3 tries, it escalates with a report of what it tried and learned.

The Control Room

One dashboard,
checked from your phone

FastAPI backend, a 2,253-line single-page app, and a streaming AI chat panel — reachable anywhere on your Tailscale network over TLS.

FastAPI + SPA

15 Python modules (3,404 LOC) drive a single-page app with live status polling, a fleet summary bar, per-machine drill-down, and one-click actions: restart, push, clear blockers.

Ask it in plain language

A streaming chat panel (SSE + markdown) lets you ask the dashboard about your machines. TLS, Caddy reverse proxy, and bearer-token auth make it safe to reach from a phone.

One glance tells you if the fleet needs you

Every machine reports one of 9 status values, mapped to 5 color buckets — healthy, warning, halted/error, stopped, offline. The summary bar auto-refreshes every 120 seconds; alert history comes from a deduplicated digest queue.

Architecture

Two-tier monitoring
replaces the monolith

The 2,325-line fleet-supervisor was one process doing everything. The new design splits concerns — and keeps the coordinator strictly read-only.

📝

Per-Machine Monitor

Runs on each machine. Writes status.yaml with health, features, problems, git HEAD age.

🏛️

Fleet Coordinator

Reads all status files, applies cross-fleet sanity checks, writes fleet-status.yaml, sends alerts.

📊

Dashboard

Serves the SPA, reads fleet-status, exposes API endpoints, hosts the chat panel.

4 Cross-Fleet Sanity Checks

  • Monitor dead or stale (status.yaml > 10 min old)
  • Self-report contradiction (claims healthy, HEAD unchanged > 1 hour)
  • Simultaneous token burn (2+ machines stopped at once)
  • All monitors dead (host-level problem)

Read-Only by Design

The coordinator never starts or stops containers. All writes go to coordinator-owned files: fleet-status.yaml, digest-queue.jsonl, last-alert.json. Alerts deduplicate on a 1-hour cooldown per condition.

Safety Layer

Passing tests isn't enough —
intent gates check the story

Green tests prove the code runs. The intent gate asks the harder question: does this feature actually serve the human's claimed user story?

1

Feature Tests Pass

Build and test succeed. The code works mechanically. But does it serve the human's intent?

2

Intent Gate Fires

The intent-gate-agent reads PROJECT-INTENT.md, the spec's Section 0, the implementation summary, and test results — cross-referencing claim against evidence.

3

Structured Verdict

PASS or FAIL with specific evidence: CLAIMED_STORY, EVIDENCE, GAPS, STORIES_ADVANCED, FEEDBACK. Incremental progress counts — practical, not pedantic.

4

Gate Enforced or Inactive

No PROJECT-INTENT.md? Gate auto-passes with a note. Missing Section 0? Hard FAIL with instructions to add it. The gate adapts to the project's maturity.

The Evolution

From “ship fast”
to “stay alive”

The earlier story proved a dev machine could ship. This one is about what happens when you have five and need to keep them alive.

Before: Ship Fast

  • One machine, one project
  • Manual monitoring via SSH
  • If it broke, you noticed eventually
  • No self-healing capability
  • Monolithic fleet-supervisor

Now: Stay Alive

  • Five machines running in parallel
  • Web dashboard from any device
  • Problems surface automatically
  • Pattern I + agent-based self-healing
  • Two-tier architecture, intent gates

The foundry doesn't just create dev machines anymore. It creates dev machines that reason about their own health, fix their own environments, and phone home when they need help — while the human just watches.
