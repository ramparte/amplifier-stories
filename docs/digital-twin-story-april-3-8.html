The Tension

Before, every iteration meant a full rebuild

Change one line and the only way to see it was to tear the whole environment down and build it again from scratch. Iteration was expensive enough that testing got skipped.

The Old Loop — Full Rebuild

Destroy environment

Re-provision from scratch

Reinstall all dependencies

Re-run readiness checks

Full teardown for every single iteration.

The Payoff

Launch once. Update in place.

The update command patches the running environment instead of rebuilding it — so the container stays alive across every iteration.

The New Loop — In-Place Update
  • Validate the environment is running
  • Optionally refresh PyPI overrides
  • Run update commands in-place
  • Re-run readiness checks

The environment stays alive across iterations.

How It Works

The profile declares the update; the engine runs it in place

# Launch once, then update repeatedly $ amplifier-digital-twin update my-env --var branch=feature-x # Skip readiness checks for rapid iteration $ amplifier-digital-twin update my-env --skip-readiness

Profile Schema

A new update section with cmds (shell commands) and refresh_pypi to rebuild PyPI overrides from current source repos.

Engine Logic

Validates the running env, optionally kills pypiserver, clears wheels, rebuilds overrides, runs update commands, then re-checks readiness.

Proven by 3 E2E Tests

New code is picked up, the environment stays running across updates, and the skip-readiness fast path works.

The Examples

Two real update profiles already ship with it

These aren't hypotheticals — they're the profiles you can copy today, one refreshing local packages and one refreshing a running server.

amplifier-user-sim

update: refresh_pypi: true cmds: - pip cache purge - pip install --upgrade amplifier-core

Rebuilds PyPI overrides from current source, clears the pip cache, reinstalls from local packages.

amplifier-chat

update: cmds: - pkill -f amplifier-chat - pip install --upgrade amplifier-chat - amplifier-chat serve &

Kills the running server, reinstalls, restarts — a clean refresh without touching the container.

Reliability

Readiness now proves ports are reachable from the host

check-readiness used to confirm a service was up inside the container. Now it confirms the Incus proxy devices actually expose it to the host — the reachability you were really trusting.

TCP + HTTP Checks

Connects via Python socket and urllib from the host process, verifying both TCP reachability and HTTP response codes per mapped port.

Configurable Retry

New PortMapping fields verify (default true), verify_timeout (30s), and verify_interval (2s) catch slow-starting services.

Tested Both Ways

E2E tests launch containers, verify access passes, stop the service, then verify access correctly fails.

Architecture

Agents carry the weight, so the root session stays light

DTU work now routes through agents, not the root session. The heavy skill loads inside agent sessions, so you only pay the token cost when DTU work is actually happening.

dtu-profile-builder

Loads the skill first, then builds and validates profiles, reporting state changes and issues back to root.

dtu-browser-tester

Loads the skill first, then runs browser-based tests against running environments with a full context handoff.

Get Started

Launch once. Iterate fast.

# Launch an environment $ amplifier-digital-twin launch my-profile.yaml # Change your code, then update in-place $ amplifier-digital-twin update my-env # Verify ports are reachable from the host $ amplifier-digital-twin check-readiness my-env # Or just ask an agent to build you a profile $ "Build me a DTU profile for testing amplifier-chat"
