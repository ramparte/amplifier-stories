The Complication

Getting agents into M365 is an authentication and permissions gauntlet

The vision was simple. The path there was auth errors, permission grants, MFA, and hidden licensing rules.

AADSTS65002: Consent between first party application '1950a258-227b-4e31-a9cf-717495945fc2' and first party resource '00000003-0000-0000-c000-000000000000' must be configured via preauthorization - applications owned and operated by Microsoft must get approval from the API owner before requesting tokens. # My reaction: "mm failed" "try device code again once and cache token"
🔐 Auth & MFA maze
  • Device Code vs Client Credentials vs ROPC — each with different limits
  • “There can be MFA” — automation accounts had to be excluded
💳 Permission & licensing gotchas
  • “Test now, I granted the permission you asked” — grant, retry, repeat
  • “Microsoft 365 E5 (no Teams) isn’t enough” — licensing surprises
The Model

I described the vision — Amplifier architected, built, and tested it

That division of labour is what turned a month of Graph-API grind into a single day. My only jobs: describe intent, grant permissions, validate.

Mechanism · Design First

Before writing a line of code, Amplifier settled the auth problem

It weighed the auth methods

Device Code Flow User signs in via browser
ROPC (chosen) Automation with user context
It scoped the capabilities
✓ Users & Groups ✓ Email ✓ Teams ✓ Calendar ✓ Planner ✓ To-Do
“Do you have an Azure AD App Registration already? What specific capabilities do you need?”

Mechanism · Safe Testing

It validated everything in throwaway shadow environments

“Use shadow environment so the current session is not compromised” — auth changes were proven in isolation before touching the real work.

# Shadow test scenario 1. Create shadow with local source: /home/colombod/amplifier-bundle-m365 2. Install Amplifier + M365 bundle 3. Configure automation credentials 4. Test ROPC delegated auth for Diego 5. Post message to Findings channel ✓ Results verified in isolation
Why shadow testing?
  • Test auth changes without breaking the main session
  • Isolated from the production environment
  • Can fail safely and retry
  • Validates the complete integration
