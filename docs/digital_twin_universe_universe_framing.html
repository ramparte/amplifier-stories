The Digital Twin Universe, Universe

Three bundles already ship on one shared substrate.

This isn't a proposal. Three entry points are live today — pick the one that matches your use case; they all run on the same Digital Twin Universe infrastructure.

reality-check

Test or validate something that is not Amplifier.

amplifier-tester

Test or validate something within Amplifier.

digital-twin-universe

Use DTU directly, or stand up parallel dev environments.

The common thread: isolated environments, stood up on demand from a declarative profile, that simulate the world the code will live in — so consumers (AI or developers) can clone, install, run, and experience it like a real user.
The Tension

“Tests pass on my machine” isn't evidence it works.

When a software factory produces a unit of work — an app, an Amplifier component, anything — one question still remains: does it actually work when a real user goes to use it? We had nothing that could seamlessly stand up an environment an agent could validate against in a way that mirrors the real world. That gap is where the digital twin in the name comes from.

From “tests pass on my machine” to “this actually mirrors what would happen in production.”
The Tension · What Came Before

Shadow-env got us only partway to production.

For Amplifier development we had the shadow environment. But it couldn't reliably mirror what happens when code is pushed to GitHub — our notion of production.

Amplifier-specific

Built for Amplifier testing. Couldn't stand up broader systems — mock services, web UIs, full user-facing stacks.

CLI-only in practice

Fine for CLI or agent-driven testing. Not useful for GUI-level experiences or beyond.

Leaky isolation

Testing could impact the dev environment. The fallback was “test in prod” or find a literally clean machine.

The Payoff

Isolated environments, on demand — real enough to trust.

The fix is a clean, non-dev environment stood up on demand that looks like a fresh user machine. The resolver (or developer) pushes changes in from the outside and tests against it. The DTU can't see the dev environment, so results are evidence, not echoes.

A clean machine the dev environment can't reach in — so what passes here is what a real user would experience.
How It Works · Infrastructure

A universe, not just a container: Incus runs whole systems.

We're building increasingly complex things autonomously — software that talks to other services, external APIs, and a whole host of dependencies. Managing that complexity needs more than a single-process container.

Incus system containers

Behaves like a lightweight VM: boots systemd, runs many processes, keeps persistent state. SSH in, install packages, manage it like a regular Linux server — without hardware-virtualization overhead.

Full VMs, same interface

Incus also manages real KVM virtual machines, so containers and VMs live side by side. That's what lets the universe closely match the end-user's actual experience.

Docker packages one app to ship it. Incus gives you lightweight Linux machines (and VMs) to use as infrastructure — which is what a universe needs.
How It Works · Mocks

Mock services stand in for the surfaces you can't hit for real.

An ecosystem of mock services lets agents and developers test against realistic surfaces — no production APIs, rate limits, or manual setup. Each can run inside a DTU or alongside it on the host.

Mock Slack

A mock Slack service apps point at like the real API — handy for amplifier-hive-slack-style scenarios with zero source-code changes.

amplifier-bundle-gitea

Ephemeral Gitea instances that mock GitHub. Mirror repos in, work freely, optionally promote back as PRs — our standard GitHub stand-in inside DTUs.

How It Works · reality-check

reality-check turns intent into acceptance tests it runs for you.

Given a conversation, spec, or project context, reality-check can derive acceptance tests automatically — or take yours explicitly, and use any combination of the two. Then it runs them in a fully isolated DTU and hands back a verdict.

Provide intent or acceptance tests → a DTU is stood up → the right tests run → a final report comes back. Completely isolated.
The Turn · An Ecosystem Emerges

Each use case that emerged became its own bundle.

Testing Amplifier itself

amplifier-tester — agents and context for Gitea + DTU testing inside the Amplifier ecosystem. It replaces shadow-env.

Testing anything else

reality-check makes browser-tester, terminal-tester, and friends work out of the box with DTUs — plus an intent analyzer that generates tests.

Parallel dev environments

Because Incus containers behave like full systems, you can stand up many isolated dev environments at once — without touching your system install.
