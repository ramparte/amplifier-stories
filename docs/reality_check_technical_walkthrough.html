Evidence In, Not Opinions

The pipeline hands back PASS with real evidence and screenshots.

amplifier-bundle-reality-check runs software inside a DTU (an isolated, disposable environment) and validates it. Here it is checking a URL-shortener web service — each validator returns the same shape: an ID, a status, and evidence.

--- browser-tester results --- | ID | Test | Status | Evidence | |----------|--------------------------|--------|--------------------------------------------| | a3f12c8b | Web UI shortens a URL | PASS | Result panel showed localhost:8080/Xk7mNq | Screenshots: 02-a3f12c8b-result-displayed.png --- generic-tester results --- | ID | Test | Status | Evidence | |----------|--------------------------|--------|--------------------------------------------| | 9d4a210e | API 302 redirect | PASS | curl -I returned 302, Location: example.com| --- terminal-tester results --- | ID | Test | Status | Evidence | |----------|--------------------------|--------|--------------------------------------------| | 7e80f3a1 | Admin CLI lists URLs | PASS | `shortener admin list` exit 0, JSON w/ code|

That evidence is the output. The rest of this walkthrough is how the pipeline earns it — trustworthily.

The Trust Problem

An LLM writing the tests and the report can quietly drift.

Every stage of this pipeline is an LLM agent: one synthesizes acceptance tests, three run them, one writes the report. Left unchecked, any of them can emit malformed YAML, invent a field, or reference a test ID that doesn’t exist. “The model said it passed” is not the same as “the output is valid.”

The question this design answers: who decides an agent’s output is good enough to pass to the next stage — and how do you guarantee it, run after run?

The Pipeline

Five steps, one recipe.

The reality-check-pipeline recipe orchestrates everything. Intent and DTU are independent — conceptually parallel — and validators only run on tests they actually own.

Intent Analyzerconversation → tests.yaml
DTU Profile Builderprofile → running env
Validatorsterminal · browser · generic
Report Agentresults → report.raw.yaml
CLI Renderreport.yaml + report.html

Two convergence loops wrap the two agents that must emit valid structured output: the intent analyzer and the report agent. That is where the trust problem gets solved next.

The Payoff

The CLI — not the LLM — is the convergence judge.

The agent writes a file; a bash step runs a deterministic validator (validate-acceptance-tests, validate-report). Non-zero exit feeds the raw errors back into the next attempt. Capped at 3 iterations, fail loudly otherwise. Convergence is a recipe property, not a model promise.

# reality-check-pipeline.yaml — convergence loop while_condition: "{{validated}} != true" max_while_iterations: 3 break_when: "{{validated}} == true" update_context: previous_errors: "{{iteration_result.validation_result.errors}}" # fed back in
Step 1 · Intent Analyzer

One tests.yaml becomes the source of truth.

The analyzer turns conversation history, an optional spec, and repo paths into structured acceptance tests — or validates a draft you hand it directly. Everything downstream keys off this one file.

Inputs

  • Full conversation history
  • Spec or README (optional)
  • Repo paths (optional)
  • or your own draft acceptance tests

Output schema

  • summary, software_type
  • entry_points — URLs, commands
  • tests[] — id, type, steps[]
  • assumptions[] — what it inferred

CLI side effect: validate-acceptance-tests auto-injects an 8-char hex id into any test missing one, then rewrites the file in place.

Step 2 · DTU Profile Builder

Stand up the universe the tests run against.

Delegated to digital-twin-universe:dtu-profile-builder, independent of the intent analyzer. It deploys the software so validators test it exactly as a real user would see it.

What it does

  • Infers ports, deps, runtime needs
  • Generates a DTU profile YAML
  • Launches with amplifier-digital-twin launch
  • Verifies readiness, hands back access

What downstream gets

  • A DTU instance ID (dtu-a1b2c3d4)
  • Forwarded URLs for browser tests
  • An exec channel for terminal tests
  • The deployed software, running

Stays running after the pipeline finishes — the user can poke at the deployed software and inspect failures interactively.

Step 3 · Validators

Three validators, one rule: only run what you own.

Each validator filters tests.yaml by type and exits immediately if no tests match. They run sequentially inside the DTU and emit the evidence tables from beat one.

terminal-tester

Owns: type: cli

Spawns CLI/TUI apps via a PTY bridge. Sends keystrokes, captures screen state, verifies output as a real user would.

browser-tester

Owns: type: browser

Drives a real browser against the DTU’s forwarded URL via a vision-capable operator. Navigates, fills, clicks, screenshots.

generic-tester

Owns: type: other

Catch-all. Runs bash inside the DTU — HTTP probes, file checks, library imports, anything reducible to “run a command, check output.”

Step 4 · Report

The agent aggregates; the CLI validates and renders.

The report agent reads tests.yaml plus the three validator blocks and writes a slim report.raw.yaml — top-level extra=forbid, only results: allowed. It doesn’t re-judge; it aggregates. Then the same convergence loop validates it and the CLI renders two artifacts.

report.yaml

Canonical, expanded. Joins on id, buckets into passed / failures / missing, computes statistics deterministically — not asked of the LLM.

report.html

Self-contained visual artifact for end users. Optional --dtu-details-file renders an “Environment Access” footer so a reader can connect to the DTU and reproduce.

Intent → tests.
Tests → evidence.
Evidence → report.

Every seam has a deterministic checkpoint — the CLI — sitting between LLM output and the next stage. That is what makes a chain of five LLM agents produce a trustworthy pass/fail.
