A human wrote the architecture spec and watched the dashboard. The machine did the rest — 445 commits, real-time collaboration, OOXML import/export, tables, deployed to Fly.io. This is the leverage working. Which makes what happens next the interesting part.
The complication
But the machine can't tell what's worth building
Tireless throughput is not the same as good judgment. The machine will happily do the next thing that is available — deterministic, spec-ready, guaranteed to pass review — forever. Whether that thing matters is a question it never asks.
STATE.yaml faithfully reported every problem. The machine doesn't lie or hide issues. It just can't prioritize — and one small, obvious feature is about to prove it.
The payoff · the honest part
The ruler it never drew: 534 sessions, zero lines
A ruler — the strip every word processor has at the top — sat in the machine's next_action field as a candidate, session after session. It grinds for hours what a person draws in seconds, because the ruler needed design judgment and the machine always had an easier, always-available task to reach for instead.

How it works
It runs one disposable loop — and the spec is the product
Strip away the tooling and it's a single cycle. Every session starts from zero context, reads the spec before it writes code, and verifies before it commits. Whatever the spec makes easy is what gets built — which is exactly why the ruler lost.
read STATE.yaml → pick next feature → spawn zero-context session → implement from spec (TDD) → verify build + test → commit → update state → repeat
Every session is disposable
It reads state, does 3–5 features, writes state, and exits. Nothing lives in a session's memory.
The spec is the product
"If your specs are good, the machine builds good software. If your specs are vague, it builds vague software."
How it stays honest
A fresh agent tries to break every feature before it counts
After each feature, a zero-context sub-agent reads the spec and the diff and actively hunts for failures. In one session it caught a bug where fontSizeCs=0 would have made text invisible — a missing >0 guard. The machine even has the spine to say no: it rejected feature F-1546 on technical merit and added a negative test so it could never return.
The catch that explains the ruler
Rigor cuts both ways. Because a test file always passes antagonistic review and always increments the counter, the machine learned to reach for tests first — and that preference quietly compounds into the pattern on the next slide.
The pivot
It optimized for completionism, not value
By session 534 the numbers told the story. The machine had found a repeatable, always-available pattern — mapping OOXML properties through six layers — and optimized for it, because user-visible work is harder and less predictable. That is the ruler incident, expressed as a ratio.

Where judgment re-enters
Before it builds, the foundry decides if it should
The /admissions process interrogates the project first — it reads the codebase, runs the commands, and scores real artifacts against gates. "It doesn't take your word for anything."
  • 1Decomposability — hundreds of small, independent units?
  • 2Verifiable correctness — fast, automatic feedback?
  • 3Sufficient architecture — enough to prevent drift?
  • 4Functioning toolchain — does build & test run?
  • 5Spec quality — specs a machine can consume?
  • 6Intent clarity — clear enough to work from alone?
Real assessment
safeguard: 15%
on Gate 4 — zero code, no build system, no toolchain chosen. The assessment prescribed exactly what to fix. Below 50% is a hard stop; 50–75% is proceed-with-caution. "No optimism bias. A 48% is a 48%."
✅After remediation, the machine ran fine — and finished 100% healthy.
The takeaway
The machine is the leverage.
The judgment stays human.
Compose a problem too big for the model into small problems it can handle, and you build things the model never could in one pass. What the machine still needs from you is priorities — the sense of what's worth building next, the ruler nobody told it to draw. And the pattern holds across projects — when it's configured right.
