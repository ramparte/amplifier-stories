The catch

A score is only as trustworthy as its harness

Those numbers mean nothing if the machinery that produced them is flaky. The harness that came before this run wasn't good enough to trust.

! Before the rebuild (old benchmarking harness)
  • Monolithic harness with linear execution
  • Infrastructure flakiness polluted agent scores — a Docker hiccup looked like an agent failure
  • Idle Docker containers wasting resources
  • Scattered config across multiple file types

If a network blip can cost an agent points, you can't tell skill from luck. That's the gap the rebuild had to close.

How it stays reliable at scale

A DAG job runner that never loses work

Evaluation is a typed directed-acyclic-graph of jobs — parallel where it can be, resumable where it must be.

Parallel execution, SQLite-persisted state for resumability, soft dependencies so partial failures never block final results, and automatic cycle detection. A crashed run picks up where it left off instead of starting over.

How fairness is enforced

Failure classification keeps agent scores clean

Every failure is triaged, so a flaky container can never masquerade as an agent mistake.

  • AGENT_ERROR — a real agent issue, so it counts against the score
  • INFRASTRUCTURE_ERROR — flaky infra, excluded from scoring
  • TEST_ISSUE — a benchmark bug, excluded from scoring

Only infrastructure errors set valid_trial=false. That single rule is what keeps the 62.5% honest.

How judgments get checked

In-container analysis, validated seven ways

When a result is worth a closer look, the harness investigates from inside the environment — and only when it's worth the cost.

  • analysis_runner.py runs inside Docker with full filesystem access to explore failures
  • A score threshold (≥85.0) skips costly analysis on clear passes
  • 7-run comparison with Kendall's W agreement measures ranking stability — the same W = 0.67 behind the payoff
