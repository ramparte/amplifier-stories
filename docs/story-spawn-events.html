The Solution

Every session now spawns
through one function

spawn_bundle() is THE unified entry point: it handles bundle resolution, config inheritance, context passing, background execution, and event emission.

The Problem

Before this, spawning was
duplicated and isolated

Every consumer reinvented session spawning — and the copies drifted apart.

📋

~400 lines duplicated

CLI and Foreman each had their own spawning logic. Same patterns, different implementations, diverging behavior.

🔇

No event communication

Sessions were islands. When Session A completed, Session B had no way to know or react.

⚙️

Manual asyncio everywhere

Background tasks required hand-rolled async patterns. No declarative way to define long-running sessions.

Phase 1A

The core primitive unifies bundle,
config, context, and execution

# New kernel events in amplifier-core class EventType(Enum): SESSION_COMPLETED = "session_completed" SESSION_ERROR = "session_error" # The core primitive in amplifier-foundation async def spawn_bundle( bundle: str | BundleConfig, instruction: str, parent_session: AmplifierSession | None = None, background: bool = False, ) -> SpawnResult: """Spawn a session from a bundle - THE unified entry point."""

Dataclass with session, task handle, and result access.

Phase 2

Sessions can finally
talk to each other

A pub/sub event system lets one session react to what another one does.

# Session A emits an event when it completes await session_a.emit_event("analysis_complete", {"findings": results}) # Session B subscribes and reacts async for event in router.subscribe("analysis_complete"): await process_findings(event.payload)

SessionEvent

Typed event dataclass with source, type, and payload.

EventRouter

Central pub/sub broker for cross-session communication.

20 test cases

Emission, subscription, timeouts, and error handling.

Phase 3

Triggers define when a session starts,
not just how

⏱️

TimerTrigger

Schedule sessions on intervals. Cron-like patterns for periodic tasks.

📡

SessionEventTrigger

React to events from other sessions. Chain workflows together.

🎯

ManualTrigger

Programmatic activation from code when conditions are met.

# One protocol, many trigger types class TriggerType(Enum): FILE_CHANGE = "file_change" TIMER = "timer" SESSION_EVENT = "session_event" WEBHOOK = "webhook"
Phase 4 & 5

Background sessions become
declarative config

No more hand-rolled asyncio — describe a long-running pool and let the manager run it. Foreman adopts it with graceful fallback.

BackgroundSessionConfig( name="code-reviewer", bundle="review:code-review", triggers=[ SessionEventTrigger("pr_opened"), TimerTrigger(interval=3600) ], pool_size=3, restart_policy="on_failure" )

Foreman uses background_sessions declaratively via an optional-import pattern, with automatic fallback to original behavior when the feature isn't present. Proven end-to-end with 6 integration tests.
