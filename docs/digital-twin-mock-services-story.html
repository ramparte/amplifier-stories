The Tension

For a software factory, testing against real Slack is a non-starter

Most real software integrates with external services — and testing those integrations creates friction that kills velocity. In a factory where agents constantly create and tear down environments, that friction compounds until testing stops happening.

🔑

Account Overhead

Slack alone needs an account, an app registration, a workspace, and OAuth tokens — multiplied for every environment.

⏱️

Rate Limits

Real APIs have quotas. Agents spinning environments up and down burn through those limits fast.

🔧

Manual Setup

Throwaway accounts, hand configuration, cleanup after every run. Non-starter for agent-driven development.

The Example

Meet amplifier-hive-slack — and the mock that stands in for Slack

amplifier-hive-slack is a bot that integrates directly with Slack's APIs. To test it for real you'd need the full account-and-token dance above. So instead we built an 822-line mock Slack that the bot talks to exactly as if it were the real thing — across four surfaces:

  • Slack Web API — 11 GET/POST endpoints (auth.test, chat.postMessage, conversations.history, reactions.add, …)
  • Socket Mode WebSocket — hello handshake, event envelopes, ack, ping/pong keepalive, rewritten to connect over TLS transparently
  • Control API — /mock/send-message, /mock/create-user, /mock/create-channel for full programmatic simulation
  • Web UI — a vanilla HTML/JS interface with channel list, message feed, and input, so you can drive the mock from a browser
The Payoff

Four themed Slack workspaces, live at once — zero real API calls

What you test is what you ship. The app is production code; only the network destination changed.

The multi-workspace demo launches four DTU environments simultaneously, each with unique channels, seeded users, and scripted conversations firing in real time — the bot responding throughout, and not one real Slack account in sight.

  • 🚀 Startup Weekend — a team building a meal-prep app in 47 hours; the bot scopes features and structures the pitch.

  • 🏘️ Oakridge HOA — a neighborhood association juggling maintenance, events, and fence disputes.
How It Works

DNS rewriting redirects api.slack.com to the sidecar — the app never changes

Traffic bound for a real API hostname is transparently redirected to the mock container. The application is installed completely unmodified; mitmproxy does all the work at the network layer.

How It Works

One DTU profile declares the mocks, the passthrough, and the launch

The profile is the single source of truth: what to install, which mocks to wire up, which real APIs to let through, and how to start the app.

# amplifier-hive-slack.yaml — DTU profile (86 lines) name: amplifier-hive-slack base: image: ubuntu:24.04 mock_services: # ← declare mocks here - source: ${MOCK_SLACK_PATH} passthrough: # ← real APIs still work allow_external: true services: - name: anthropic key_env: ANTHROPIC_API_KEY provision: # ← install & launch setup_cmds: - uv tool install amplifier-hive-slack - nohup hive-slack config.yaml &
How It Works

You own the mock, so you script the entire scenario

Because the mock is yours, the Control API lets you stage any workspace topology and drive it end to end — the same lever behind the four-workspace demo.

♾️

No Limits

No quotas, no accounts, no cleanup. Tear down and rebuild in seconds, a thousand times over.

What You Keep

Once a mock exists, everyone reuses it — for any external service

Mocks are standalone repos with a standard digital-twin-mock.yaml. A profile just declares what it needs; DTU clones, builds, starts, and rewrites DNS. Pair it with the browser-tester agent and the loop closes — end-to-end verification with zero real external calls.
