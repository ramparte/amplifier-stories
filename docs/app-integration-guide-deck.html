Core Concept

Your app and Amplifier meet
at one clean boundary

This is the Protocol Boundary Principle: a thin bridge where app events become Amplifier operations and Amplifier events become app outputs. Neither side knows the other's internals — which is exactly why you get testability, portability, and clarity for free.

The Boundary

The boundary is exactly
four protocol points

Each is a call from Amplifier out to your app. Amplifier decides when; your app decides how.

Protocol PointDirectionYour app decides
ApprovalSystemAmplifier → AppHow to present a confirmation — modal, Slack button, or CLI prompt — and return the decision.
DisplaySystemAmplifier → AppThe rendering medium when an agent shows something — WebSocket message, Slack block, terminal output.
StreamingHookAmplifier → AppWhere to forward every session event — content deltas, tool status, thinking — over your transport.
Spawn CapabilityAmplifier → AppHow new sessions get created for delegation, sub-tasks, or parallel analysis — the universal entry point.

# Steps 1-3: Once at startup bundle = await load_bundle("./bundle.md") prepared = await bundle.prepare() # Steps 4-7: Per interaction session = await prepared.create_session( session_id="my-session-001", approval_system=my_approval, display_system=my_display, ) response = await session.execute("Hello!")

PreparedBundle is your singleton

prepare() is expensive — it downloads modules and resolves dependencies. Do it once at startup.

create_session() is cheap — it produces an ephemeral session from the cached bundle. Do it per request.

Choosing a Pattern

Match your app type to
one of five session patterns

Application TypePatternLifespanKey Concern
REST API / webhookA: Per-RequestSecondsPreparedBundle singleton
Chat bot / messagingB: Per-ConversationMin–HoursSession map + per-session locks
Personal AI assistantC: SingletonDays–WeeksPersistence + compound intelligence
Voice assistant + toolsD: Voice BridgeSessionTool boundary, not orchestrator replacement
Multi-persona / tenantE: Multi-SessionVariesRouting + resource management

🔑 Pattern D insight

The voice model is NOT inside AmplifierSession — it has its own connection and state. Amplifier is a tool backend, not the orchestrator of the voice conversation. Audio never touches Amplifier; only text (tool calls, results) crosses the boundary.

Avoid These

Skip the boundary and you
reimplement Amplifier badly

Direct API Calls

Calling anthropic.messages.create() directly and parsing tool calls by hand. You've rebuilt the orchestrator — without hooks, streaming, or error recovery.

Hand-Rolled Tool Loops

A while True loop that calls the provider, checks for tool calls, executes them. That is the orchestrator's job — it already handles streaming, hooks, and recovery.

Fat Bundle Per-Request

Calling prepare() on every request, re-downloading modules each time. Fix: prepare once at startup, then create sessions cheaply.

The common thread: each one crosses back over the boundary and gives up what Amplifier already provides. Stay on your side of the seam.
