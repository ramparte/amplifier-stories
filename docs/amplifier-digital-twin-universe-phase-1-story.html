Digital Twin Universe · Phase 1 demo

A from-scratch install unknowingly ran unpublished local changes

A Digital Twin is a complete, isolated environment stood up on demand. In the demo, local edits to amplifier-core and the provider-anthropic module lived only inside it — then a clean install pulled them in as if they were the real published packages.

1

Push local, unpublished changes into the twin

Bump the amplifier-core version and add a print statement to the provider module — changes that exist nowhere on real PyPI or GitHub.

2

Install Amplifier from scratch inside the twin

uv tool install git+https://github.com/microsoft/amplifier — exactly as a brand-new user would, no special flags.

3

The modified wheel and rewritten provider are live

Run Amplifier: the local amplifier-core wheel and the rewritten provider are active — transparently, with no idea they were redirected.

AI verifies in the very environment it built in — so context poisoning, deployment blind spots (packaging, installs, config), and external-service hell all hide until someone installs it fresh. That gap is exactly what the demo closed.

The core promise

The software inside the twin has no idea it's in a twin.

It thinks it got everything from PyPI and GitHub. No special configuration, no test flags — just reality, redirected. That's what makes a "tests pass" from inside the twin actually mean "this works when deployed."

The artifact behind it

One YAML profile declares the whole universe

amplifier-user-sim.yaml is the single declarative file that says what the twin contains — base image, what to redirect, what to override, what to forward. Everything downstream reads from it.

name: amplifier-user-sim base: image: ubuntu:24.04 url_rewrites: rules: - match: github.com/microsoft/amplifier-module-provider-anthropic target: ${GITEA_URL}/admin/amplifier-module-provider-anthropic pypi_overrides: packages: - name: amplifier-core wheel_from_git: repo: ${GITEA_URL}/admin/amplifier-core.git build_cmd: uv run --with maturin maturin build --release passthrough: services: - name: anthropic key_env: ANTHROPIC_API_KEY
How the redirection works

GitHub and PyPI quietly resolve to your local source

Two rules in the profile do the transparent sleight of hand that fools the software into thinking nothing changed.

🌐

URL rewrites

mitmproxy redirects GitHub URLs to local Gitea repos transparently — a git+https://github.com/... clone actually lands on your modified copy.

📦

PyPI overrides

Wheels are built from local source and served by a local pypiserver, so pip/uv install your modified packages instead of the published ones.

Why this isn't a mock-up

It's real today — E2E-tested, four scenarios working

Phase 1 already proves the full flow end-to-end: profile-driven launch, transparent rewrites, PyPI overrides, credential passthrough, and ephemeral lifecycle — verified from launch through install to run.

  • 01
    Core + module changes together. Local edits to amplifier-core (PyPI) and modules (git-based) validated in one fresh environment.
  • 02
    Single-module rewrite. Change just one module without touching core — the amplifier-user-sim-single-module profile handles it.
  • 03
    Fresh-install simulation. Confirm uv tool install works with your changes, exactly as a real user would experience it.
  • 04
    Iterative development. Push changes, destroy, relaunch clean, repeat until confident.
Where it's going · how to start

Phase 1 today, a whole mock-service universe next

Next up: a catalog of mock services (M365, Slack, GSuite) with no rate limits, graphical human access, agent interaction surfaces, and DNS-level rewriting — so an entire deployed world can be simulated on demand.
